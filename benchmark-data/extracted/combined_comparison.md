## Per-row notes

- **Cold startup vs Android CompilationMode.Partial (baseline profile)** — *COMPARABLE (caveats)*: Android timeToInitialDisplay vs iOS AppLaunch signpost: both bound process launch -> first frame. Different instrumentation. Android side used CompilationMode.Partial(BaselineProfileMode.Require), i.e. only baseline-profile methods AOT-compiled.
- **Cold startup vs Android CompilationMode.Full (full AOT)** — *COMPARABLE (caveats)*: Same iOS side. Android used CompilationMode.Full(), i.e. everything AOT-compiled. Despite the name, 'Full' is not the unoptimised path - it is the most-compiled one, and here it is slower than Partial.
- **Warm startup** — *NO_DATA*: iOS: XCTOSSignpostMetric.applicationLaunch emits no interval on app.activate() (no process launch), so 0 measurements were recorded in both iOS targets.
- **Hot startup** — *NO_DATA*: Same root cause as warm startup.
- **Scroll (steady-state)** — *NO_DATA*: iOS: scrollDecelerationMetric recorded 0 measurements; Compose Multiplatform does not emit the UIScrollView deceleration signpost. Android metric is frame-based and has no iOS counterpart anyway.
- **Fast-scroll stress** — *NO_DATA*: Same root cause as scroll.
- **Initial data load** — *NOT COMPARABLE*: Android measures an in-process trace section around the network fetch only (~215 ms). iOS measures whole-scenario wall clock (launch + element wait + terminate), of which ~22 s is accessibility lookup timeout. See Task 2.
- **Category filter** — *NOT COMPARABLE*: Android measures the repository call (~5 ms). iOS measures UI wall clock containing two hardcoded sleep(1) calls, so >=2 s of the 3.18 s median is deliberate sleep.
- **Search** — *NO_DATA*: iOS KMP run was cancelled before any test executed (0 tests). Native iOS run executed 0 tests.
- **Image loading** — *NOT COMPARABLE*: Android metric is frameCount; iOS metric is wall clock containing sleep(2)+sleep(1), so >=3 s of the 4.36 s median is deliberate sleep. Different quantities entirely.
